# 补丁交付与校验

交付的补丁要同时满足两条：在用户当前的远端分支上能干净应用；应用后的文件和你验证过的完全一致。少了任何一条，用户都要多来回一轮。

## 步骤

1. **开工前同步远端**
   - `git fetch origin`，看 `git log --oneline -5 origin/main`。
   - 用户可能已经应用并推送了你的上一个补丁。`git am` 会生成新的哈希，哈希对不上是正常的，用 `git diff --stat <你验证过的提交> origin/main` 判断内容是否一致。
   - 远端有用户自己的新提交时，先 `git show --stat <提交>` 读一遍。用户改了文案、删了功能、加了工具，后续改动要沿用，不要覆盖回去。
2. **在最新的远端上开分支**：`git checkout -b feat/<主题> origin/main`。
3. **用户还没应用上一个补丁时**：把新改动 `git commit --amend` 进同一个提交，交付一个合并后的补丁。删除旧的输出文件，并明确告诉用户只用新的。
4. **先重新生成派生文件再提交**：字体子集、图标表、设计导出这类由脚本生成的文件要和源码同步，否则补丁里源码和产物对不上。
5. **写提交信息**（中文）：
   - 第一行：`feat: …` 或 `fix: …`，一句话说清改了什么。
   - 正文：用「- 」列要点，和用户提的需求逐条对应。
   - 最后一条：「验证：…」，写清楚编译了什么、跑了哪些交互。数字以脚本输出为准，比如新增图标数要按去重后的算。
6. **导出补丁**：`git format-patch -1 HEAD --stdout > <输出目录>/<项目>-<主题>.patch`；有多个提交时用 `origin/main..HEAD`。
7. **全新克隆校验**：`bash scripts/verify_patch.sh <远端地址> <补丁…> --tree <你的工作目录>`。脚本会克隆远端、按顺序 `git am`，再和你验证过的工作目录逐文件比较，图片等二进制文件也一起比。
8. **告诉用户怎么用**：
   - 给出带绝对路径的命令：`git -C <项目根目录> am --3way <补丁绝对路径>`，然后 `git -C <项目根目录> push`。
   - 多个补丁时写清顺序；说明补丁基于哪个远端提交、已经在全新克隆上验证过。

## 坑

- `git apply --check` 通过不代表结果正确，一定要应用后和验证过的文件对比。
- 远端在你工作期间又前进了：交付前再 `git fetch` 一次，必要时把改动挪到新的远端上（`git stash` → 从新的 `origin/main` 开分支 → `git stash pop`）。
- 截图、GIF 这类临时产物不要进仓库，除非放在项目约定的目录里。
- 回复和提交信息里的事实要和实际一致，发现说错了就修正并 amend，不要将错就错。
